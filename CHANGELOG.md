## 📌 Versioning Format

Versions follow the structure:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
1.2.3
│ │ │
│ │ └── PATCH → Bug fixes and minor corrections
│ └──── MINOR → New backward-compatible features
└────── MAJOR → Significant or breaking changes
```

### Examples

```text
1.0.0 → Initial stable release
1.1.0 → New portfolio feature
1.1.1 → Bug fix
2.0.0 → Major redesign or architecture change
```

# 📝 Commit Convention

The repository follows a **Conventional Commits-inspired** format.

```text
<type>: <description>
```

Common commit types include:

| Type | Purpose |
|---|---|
| `feat` | New functionality |
| `fix` | Bug fix |
| `docs` | Documentation update |
| `style` | UI or formatting changes |
| `refactor` | Internal code restructuring |
| `perf` | Performance improvement |
| `test` | Testing-related changes |
| `chore` | Maintenance work |

Examples:

```text
feat: add project showcase section
```

```text
fix: resolve mobile navigation issue
```

```text
docs: update portfolio documentation
```

```text
perf: optimize portfolio assets
```

# 🏷️ Release Guidelines

Before publishing a new release:

1. Verify all portfolio functionality.
2. Test responsive layouts.
3. Validate navigation and external links.
4. Check browser console for errors.
5. Review accessibility where applicable.
6. Review changed files.
7. Update this changelog.
8. Commit the release changes.
9. Push changes to the production branch.
10. Verify the deployed GitHub Pages website.

# 📋 Changelog Maintenance

When making meaningful changes, update the `[Unreleased]` section first.

Example:

```markdown

### Added

- Added project filtering functionality

### Fixed

- Fixed mobile navigation alignment

### Performance

- Optimized portfolio images
```

When preparing a release, move those entries into a versioned section:

```markdown
## [1.1.0] - YYYY-MM-DD

### Added

- Added project filtering functionality

### Fixed

- Fixed mobile navigation alignment

### Performance

- Optimized portfolio images
```
